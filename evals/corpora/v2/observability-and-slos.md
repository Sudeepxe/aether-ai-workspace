# Observability and Service Level Objectives

## Overview

Aether exposes its own internal behavior as metrics, structured logs, and traces, on the theory that a system nobody can observe in production is a system nobody can actually operate with confidence. The metrics are deliberately organized around a small number of dashboards, each aimed at a specific operational question — is the system fast enough, is spending under control, is the ingestion queue keeping up — rather than one undifferentiated wall of every number the system happens to produce.

## Metrics

Every metric Aether exposes is a real, live measurement of the running system, never a static or hardcoded placeholder value standing in for a number nobody has actually measured yet. HTTP request duration is recorded as a histogram broken down by method, route, and status code, which is what powers latency-percentile tracking per endpoint. The outbox's age — how long the single oldest undispatched message has been waiting — and its dead-letter depth are both tracked as gauges, since both are exactly the kind of number that matters as a current snapshot rather than as something you'd want summed or averaged over time. Language model provider calls report their own time-to-first-token duration, broken down by provider, model, and outcome, alongside a separate counter specifically for fallback events, broken down by which provider was skipped and why, so that a sudden spike in fallbacks against one specific provider is immediately visible as a distinct signal rather than being buried inside an aggregate latency number.

## Security-Relevant Metrics

A handful of metrics exist specifically to surface security-relevant events that should be rare, rather than to track routine operational volume. Refresh-token-reuse detections are counted separately from ordinary authentication traffic, since a genuine reuse detection is a strong signal of a compromised session and the metric's expected value in normal operation is close to zero. Row-level-security violations reaching the application's HTTP layer are also counted on their own, and this metric's expected value in correct operation is exactly zero at all times — any nonzero reading means a cross-tenant access attempt actually reached far enough to be observed at the HTTP layer, which by design should never happen given the two independent isolation layers described in Aether's tenancy documentation. Both of these metrics are treated as page-grade alerts precisely because their normal, healthy baseline is silence.

## Dashboards

Metrics are grouped into a small number of purpose-built dashboards rather than one shared view. A latency dashboard tracks the request-duration histograms against the deployment's declared service level objectives. A cost dashboard tracks cumulative spend against both the global monthly cap and each workspace's own budget, alongside the gap between pre-request estimated cost and actual settled cost, which is the signal for whether admission control's conservative estimate is running too far from reality in either direction. An ingestion dashboard tracks queue depth, dead-letter depth, and per-stage duration through the pipeline, so that a slowdown can be attributed to a specific stage — scanning, chunking, or embedding — rather than only showing up as a vague overall backlog. An AI-plane dashboard specifically tracks provider health: time-to-first-token, fallback frequency per provider, and circuit breaker state transitions.

## SLO Tiers

Aether's demo deployment topology is explicitly a single-node topology rather than a highly available one, and it is held to a corresponding service level objective tier rather than pretending to a higher one it cannot actually deliver. This tier commits to a lower percentage of guaranteed uptime than a multi-node, highly available deployment would target, and that gap is a deliberate, published trade-off rather than an unstated limitation — the path to a higher-availability tier is documented separately as a future upgrade rather than being silently implied to already exist. On-call coverage for this deployment topology is described as best-effort rather than a guaranteed response-time commitment, which is consistent with the single-node topology's own honestly-stated tier rather than being a separate, unrelated gap.

## Tracing

Individual requests can be traced end to end as they pass through Aether's services, with a sampling ratio applied so that not every single request generates full trace data, which would be prohibitively expensive to store and mostly redundant at any meaningful production request volume. The default sampling ratio is set so that at least ten percent of requests are traced, which is treated as enough to catch systemic patterns and intermittent problems without needing to capture every request in full detail. When no trace collector endpoint is configured, tracing falls back to a genuine no-op rather than silently buffering spans that go nowhere or throwing an error — a development environment without the observability stack running simply produces untraced requests, honestly, rather than a half-broken tracing pipeline.

## Structured Logging and the Audit Log

Separately from metrics and traces, Aether maintains a structured audit log recording security- and governance-relevant actions as discrete, durable rows rather than as ordinary application log lines that might roll off after a retention window. Actions like a membership role change, a workspace deletion request, an API key being created or revoked, and an invitation being issued all produce an audit log entry, each one carrying which workspace it happened in, when it happened, and which authenticated actor performed it. This audit log is deliberately separate from the metrics described earlier: a metric like the row-level-security-violation counter answers "how often is something happening," aggregated across every occurrence, while the audit log answers "what exactly happened, on this specific record, by this specific actor," which a metric's aggregate count can never reconstruct after the fact. Audit log entries for actions taken outside the context of any specific workspace — like a user logging in before they've selected a workspace at all — are recorded with no workspace identifier attached, rather than being forced into an arbitrary or misleading one.

## Alerting Philosophy

Not every metric Aether tracks is wired to page anyone. A metric whose healthy value is expected to fluctuate under normal load, like ordinary request latency, is tracked against a percentile threshold tied to the deployment's declared service level objective rather than triggering an alert on every individual slow request. By contrast, a metric whose healthy value is expected to be exactly zero at all times, like the row- level-security-violation counter, is wired as a page-grade alert on any nonzero reading at all, without needing a sustained-duration or percentage threshold first, since even one occurrence already represents a real security-relevant event worth waking someone up for rather than something to average over a time window.
