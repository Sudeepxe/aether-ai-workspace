# LLM Router and Provider Fallback

## Overview

Aether never talks to a single hardcoded language model provider. Instead, every generation request passes through an internal router that is aware of zero, one, two, or three configured providers at once, and that treats generation as provider-agnostic all the way down to the streaming interface the rest of the system consumes. If no provider is configured at all, the router is replaced entirely by a harmless placeholder generator that echoes retrieved context back to the caller, so that a development environment with no real API key still produces a coherent, honestly-labeled response rather than a broken one. The router's own configuration decides which providers are active and in what order they should be tried, but the decision of which provider actually answers a given request also depends on each provider's recent health, tracked independently.

## Provider Adapters

Each real provider Aether can talk to — currently OpenAI, Anthropic, and Groq — is wrapped behind an identical internal interface exposing three things: a name, a list of capabilities describing which models the adapter can serve along with their context window and cost figures, and a streaming completion method that yields text deltas and a final usage summary. Groq and OpenAI both expose an OpenAI-compatible wire format, so Aether implements the actual HTTP streaming and server-sent-event parsing logic exactly once and both of those adapters are thin wrappers around the same shared code, differing only in which base URL and API key they use. Anthropic's wire format is different enough — a separate system field instead of a system-role message, and named streaming events instead of one uniform event type — that it gets its own adapter, though it still conforms to the same three-part interface everything else does. Every adapter reports its own per-model cost figures rather than sharing one number across every model it might be configured with, because applying one provider's price to every model it could possibly serve would produce a plausible but wrong number the moment a cheaper or more expensive model within that same provider's catalog was actually configured.

## Fallback Chain and Model Selection

Providers are tried in a fixed order determined by which provider keys are actually configured: OpenAI first if configured, then Anthropic, then Groq. This order is also the fallback order — if the first provider in the chain fails in a way the router considers retryable, the router moves on to the next configured provider rather than surfacing the failure immediately. The first entry in this ordered chain is also treated as the router's primary model for reporting purposes, meaning whichever provider is listed first is the one whose model name shows up as the default answer to "which model is currently primary," even though any request might actually be served by a later provider in the chain if the primary is unhealthy at that moment.

## Circuit Breaker

Each provider has its own independent circuit breaker tracking that provider's recent call history, entirely separate from every other provider's breaker. A breaker starts closed, meaning calls to that provider proceed normally. After three consecutive failures against that specific provider, its breaker opens, and while open, the router skips that provider entirely without even attempting a call, moving straight to the next provider in the chain. An open breaker does not stay open forever; after a cooldown period of thirty seconds it transitions to a half-open state, in which the next call to that provider is allowed to proceed as a test. If that test call succeeds, the breaker closes again and normal traffic resumes; if it fails, the breaker reopens and starts its cooldown over. Because each provider's breaker is independent, one provider having a bad day does not affect how the router treats a completely different, independently healthy provider — the router only ever skips the specific provider whose breaker happens to be open.

## Retry Semantics

The router will only ever retry a failed generation by falling back to a different provider before the very first piece of text has been streamed back to the caller. Once even one token has reached the client, a mid-stream failure from that provider is surfaced as a real, hard error instead of being silently retried against a different provider, because retrying at that point would mean either duplicating content the client already received or garbling the response with a second, differently-worded attempt spliced onto the first. This rule exists specifically because streaming responses are delivered incrementally as they are generated, not buffered and sent all at once, so the router genuinely cannot take back content that has already left the building. A provider error is only eligible for fallback at all if the provider adapter itself marks that particular error as retryable; a request that is fundamentally malformed, for instance, is not something a different provider would handle any better, so the router raises immediately instead of wasting time working through the rest of the fallback chain.

## Cost Accounting

Every successful generation reports how many prompt tokens and completion tokens it consumed, and the router converts that into a cost figure expressed in microcents, where one microcent is one hundred-millionth of a US dollar. The conversion uses each specific model's own per-thousand-token prompt and completion prices, looked up from the capability the router recorded for the exact provider-and-model pair that actually served the request, never a generic or averaged figure. This per-model lookup is deliberate: two different models served by the same provider can have substantially different prices, and using one shared number across a provider's whole catalog would silently misreport spend the moment a workspace's configured model changed. Before a request is even admitted for generation, a separate, coarser pre-request estimate is computed from a local token count and a conservative worst-case per-thousand-token rate, so that admission control never needs its own capability registry and can enforce a budget ceiling using only information it already has locally.

## Concurrency Limits

Aether bounds how many generations can be in flight against any single provider at once, independent of how many different tenants are issuing requests. This exists specifically so that one workspace sending a burst of concurrent chat messages cannot exhaust a shared provider connection pool and starve every other workspace's requests to that same provider. The concurrency limit is enforced with a semaphore held for the entire duration of a streaming generation, not just for the moment the request is issued, because the resource actually being protected is the provider connection itself for as long as tokens are still arriving, not merely the instant the call begins.

## Provider Capability Registry

Each provider adapter reports a small registry describing every model it can serve: the model's maximum context window in tokens, whether it supports tool or function calling, whether it accepts image inputs, and its per-thousand-token prompt and completion prices. This registry is where the router looks up cost figures for settlement, but it is also consulted before a request is ever sent, to decide whether a given model can even accept the request being built — a workspace configured to attach an image to a chat turn against a model whose capability entry declares no vision support would be rejected at this stage rather than sent to the provider and failing there instead. An adapter configured with a model name absent from its own capability registry is treated as a startup-time configuration error rather than something silently tolerated at request time: reusing a different model's context window or price for a model nobody has actually verified would produce numbers that look plausible but are quietly wrong, and a loud failure at startup is preferable to that. This registry is deliberately kept small and explicit rather than trying to mirror an entire provider's public catalog, since a provider's available models and prices change on their own schedule, independent of any release of Aether itself, and a stale, unverified entry is worse than no entry at all.
