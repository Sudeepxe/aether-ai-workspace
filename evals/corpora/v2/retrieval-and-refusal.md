# Hybrid Retrieval and Grounded Refusal

## Overview

Aether answers questions about a workspace's uploaded documents by combining two independent search strategies over the same chunk store and fusing their results before handing anything to the language model. The two legs are a vector leg, which ranks chunks by cosine similarity between the query embedding and each chunk's stored embedding, and a lexical leg, which ranks chunks using Postgres full-text search against a generated `tsvector` column. Neither leg is trusted alone. A pure vector search misses exact identifiers, product codes, and acronyms that an embedding model tends to blur together, while a pure lexical search misses paraphrases and synonyms that never share a keyword with the query. Running both and combining their rankings is what lets Aether answer a question phrased informally against a document written formally, and still surface a chunk that only matches because it contains an exact part number the user typed verbatim.

## Reciprocal Rank Fusion

The two ranked lists are combined using Reciprocal Rank Fusion, commonly abbreviated RRF. For each chunk, RRF sums a score contribution from every leg in which that chunk appeared, where the contribution from a given leg is one divided by a constant plus the chunk's rank position in that leg's result list. A chunk ranked first in the vector leg contributes more than a chunk ranked tenth in the same leg, and a chunk that appears near the top of both legs accumulates a larger combined score than a chunk that only appeared in one. The constant added to the rank before dividing is set to sixty, which is RRF's conventional default across the information-retrieval literature and is not something Aether has tuned against its own data. RRF fuses by rank position rather than by the legs' raw scores, because cosine similarity and text-search rank are not on comparable scales and inventing a normalization between them would be more arbitrary than simply trusting each leg's own ordering. The fused score for a chunk is later exposed to the refusal gate as an absolute, un-normalized quantity: it is not rescaled to sit between zero and one for any particular query, because a rescaled value would always make the best-ranked chunk of any query look like a strong match, even when every candidate is actually irrelevant.

## Diversity Selection

After fusion produces one ranked list, Aether does not simply take the top few chunks. It runs a second pass called Maximal Marginal Relevance, or MMR, over a candidate pool drawn from the fused ranking. MMR balances two competing signals for each remaining candidate: how relevant the candidate is to the query, and how similar the candidate is to chunks already chosen for the answer. A chunk that is highly relevant but nearly identical to a chunk already selected contributes little new information, so MMR deliberately trades some relevance for diversity once redundancy appears. The balance between the two signals is controlled by a weighting constant set to one half, meaning relevance and diversity are treated as equally important by default. This diversity penalty uses cosine similarity between chunk embeddings; a chunk that arrived only through the lexical leg and has no embedding yet is treated as maximally diverse from everything else rather than excluded, since a missing embedding should never silently remove an otherwise-relevant lexical match from consideration.

## Chunking

Before any of this search machinery runs, source documents are split into chunks during ingestion. Aether's chunker targets roughly five hundred and twelve tokens per chunk, with eight hundred tokens as a hard ceiling it will not exceed even mid-sentence boundary constraints. Chunks carry a ten to fifteen percent overlap with the chunk that preceded them, so that a sentence discussing one idea which happens to fall right at a chunk boundary still has enough surrounding context on both sides to remain interpretable in isolation. The chunker never splits a sentence in half; it accumulates whole sentences until adding the next one would exceed the target, then closes the chunk. Overlap is carried forward within a section but is deliberately not carried across a heading boundary, on the theory that the next section is starting a new idea and dragging trailing content from the previous section into it would blur that boundary rather than help. Each chunk records which heading was deepest and most recently active when the chunk closed, in a field called the section path, along with the page range it spans if the source document had pages.

## The Two-Gate Refusal Protocol

Aether is designed to refuse to answer rather than guess when a workspace's knowledge base genuinely does not contain the answer to a question. This refusal decision happens at two separate points, referred to internally as Gate One and Gate Two, and both must independently agree that an answer is warranted before the user sees anything beyond a refusal message. Gate One runs immediately after retrieval and before any call to a language model: it compares the top fused RRF score against a calibrated threshold, and if the score does not clear the threshold, the turn short-circuits with the exact refusal string and no generation call happens at all. This is a real cost optimization as much as a safety measure, since a language model call that was always going to be told to refuse is a call worth skipping entirely. Gate Two is enforced by the system prompt handed to the language model itself: the model is instructed to answer strictly from the retrieved context and, if that context does not contain the answer, to reply with the exact same refusal string Gate One would have produced. Gate Two exists because Gate One's score-based check is a coarse, retrieval-level signal; it can clear the threshold on a chunk that is topically related to the query without actually containing the specific fact being asked about, and only the language model reading the chunk's actual content can catch that case.

## Threshold Calibration

The threshold Gate One compares against was calibrated, not guessed, by collecting the real fused RRF score for every genuinely answerable query in an early golden evaluation set, then setting the threshold to half of the weakest observed score among those genuine positive matches. This gives the threshold headroom to comfortably clear every known-good match while still sitting meaningfully above zero rather than accepting anything at all. The calibration is explicitly tied to one specific embedding model and would need to be redone if the embedding model or its version ever changed, because a different embedding model produces different absolute cosine similarity values and the same numeric threshold would no longer mean the same thing against a different model's output distribution. The calibration that has actually been run so far only used answerable queries as positive examples; it has not yet been stress-tested against queries that sound answerable but are not, asked against a workspace whose knowledge base is genuinely populated with adjacent, competing content rather than empty.

## Degraded Mode

The vector leg of hybrid search depends on Aether's own Postgres-backed index and can fail for reasons that have nothing to do with any individual query: a lost connection, a query that exceeds its timeout, or an index that is temporarily unavailable while being rebuilt. When the vector leg fails for one of these specific, recognized reasons, Aether does not fail the whole retrieval operation. It falls back to lexical-only results and marks the response as degraded, so the caller can choose to surface that fact to the user rather than silently returning a weaker answer that looks identical to a normal one. This degraded fallback is deliberately narrow: it only triggers for a specific, enumerated set of infrastructure-level failures, never for an unexpected programming error in Aether's own code, because silently degrading in response to a genuine bug would hide the bug behind a response that looks like everything is working normally.
