# Authentication and Session Lifecycle

## Overview

Aether authenticates end users with short-lived signed access tokens paired with longer-lived refresh tokens, and separately authenticates automated callers with long-lived API keys that follow an entirely different lifecycle. These are two distinct authentication mechanisms serving two distinct kinds of caller, and neither one is a special case of the other. A human logged into the web interface always carries an access token; a script or integration calling Aether's API directly always carries an API key. Both mechanisms ultimately resolve to the same internal notion of an authenticated caller with a set of workspace memberships, but the tokens themselves are issued, verified, and revoked through completely separate code paths.

## JWT Access Tokens

An access token is a signed JSON Web Token using the EdDSA algorithm, carrying a short expiry deliberately set to fifteen minutes. This short lifetime is a deliberate blast-radius decision: an access token that leaks is only useful to an attacker for fifteen minutes before it stops verifying on its own, without Aether needing to do anything else. Every signing key carries a key identifier, referred to as a kid, embedded in the token's header, so that the verifying side always knows exactly which key to check a given token's signature against even if multiple keys are valid at once. During a signing-key rotation, Aether can be configured with both a current signing key and a previous signing key simultaneously; the previous key is verify-only and is never used to issue new tokens, but any access token that was already signed with it before the rotation continues to validate normally until it naturally expires on its own fifteen-minute clock. This overlap window means a signing-key rotation never has to forcibly invalidate every already-issued session at the moment of rotation.

## Refresh Token Rotation

Because access tokens are so short-lived, a logged-in session actually depends on a separate refresh token to stay logged in without asking the user to re-enter a password every fifteen minutes. A refresh token has a much longer lifetime, measured in days rather than minutes, and every time it is used to obtain a new access token, Aether also issues a brand new refresh token and immediately marks the one that was just used as consumed. This is refresh token rotation: a refresh token is designed to be usable exactly once. A short grace window of thirty seconds exists after a refresh token is marked consumed, specifically to tolerate a client that fires two refresh requests in quick succession due to a network retry or a race between two browser tabs, without that overlap being treated as malicious reuse.

## Refresh Token Reuse Detection

Outside that narrow grace window, a refresh token being presented a second time after it has already been marked consumed is treated as a serious signal, not an ordinary error. Aether interprets reuse of an already- consumed refresh token as evidence that the token was stolen: a legitimate client would never present a token it had already exchanged and thrown away, so a second presentation almost certainly means an attacker captured the token in transit or from storage and is now racing the legitimate client to use it. When this reuse is detected, Aether does not simply reject the one reused token. It revokes the entire family of sessions descended from that original refresh token, on the theory that if one token in a rotation chain was compromised, an attacker may already be holding a more recent token further along the same chain, and only revoking the whole family closes that door. This reuse detection is tracked as a security metric precisely because it should be an exceptionally rare event in normal operation.

## API Keys

An API key is a long-lived credential intended for automated callers rather than interactive human sessions, and it does not expire on any fixed schedule the way an access token does. Instead, an API key remains valid until it is explicitly revoked. Each API key is scoped to exactly one workspace at creation time and carries a prefix that encodes which environment it was issued in, so that a key generated against a development environment is visibly distinguishable from one generated against production simply by looking at its prefix, without needing to look up any additional metadata. API key authentication is tracked as an anomaly- monitoring signal in its own right: a sudden spike in failed API key attempts, or the very first successful use of a brand new key, are both the kind of volume and novelty signals worth watching for unusual activity, separate from the refresh-token-reuse signal described above.

## Key Rotation

Rotating the signing key used for access tokens is an operational procedure with a defined overlap window rather than an instantaneous cutover. The previous signing key is kept configured as verify-only for as long as the longest access-token lifetime that could still be outstanding when the rotation happens, which in practice means the overlap only needs to last slightly longer than fifteen minutes to guarantee that every token issued under the old key has had a chance to naturally expire. Outside of an active rotation window, only a single signing key is configured at all; the previous-key fields exist specifically to support this temporary overlap and are otherwise left unset.

## Enumeration Safety

Aether deliberately collapses several distinct failure reasons into one identical, indistinguishable error response wherever revealing which specific reason occurred would let an outside caller enumerate valid accounts or tokens one guess at a time. A login attempt against an email address that does not exist at all produces exactly the same response as a login attempt against a real account with the wrong password; a caller cannot use Aether's own error response to learn whether a given email address even has an account. The same principle applies on the token- verification side: an access token that is expired, one that carries a malformed signature, one signed under a key id Aether does not recognize, and one that is simply garbage all produce the same generic verification failure rather than a distinct error per cause. This is treated as a security property in its own right, not an incidental simplification, and any future error path that might reveal one of these distinctions is expected to be caught and collapsed the same way before it ships.
