# Workspace Tenancy and Budgets

## Overview

Every piece of data in Aether belongs to exactly one workspace, and a workspace is the fundamental unit of tenant isolation across the whole system. Documents, chat threads, messages, budgets, and membership records all carry a workspace identifier, and a caller can only ever see records belonging to a workspace they actually belong to. This isolation is enforced in two independent, overlapping layers rather than just one, on the theory that a single layer of defense against cross-tenant data leakage is not enough for something this consequential.

## Row-Level Security

The first and deepest layer of isolation is enforced directly by Postgres itself, using row-level security policies attached to every tenant-scoped table. Before any query runs, the connection handling a request sets a session-local configuration value identifying which workspace the current request is scoped to, and Postgres's own row-level security policies use that value to silently filter every query against tenant-scoped tables down to only the rows belonging to that workspace, regardless of what the application code's own query actually asked for. This means that even if a bug in Aether's own application code forgot to add an explicit workspace filter to some query, the database itself would still refuse to return rows from a different tenant. The second layer sits above this: application code is also expected to pass an explicit, type-enforced workspace identifier into every tenant-scoped repository call, so that the database's row-level security is a backstop underneath an intentional filter, not the only filter that exists.

## Membership Roles

A user's relationship to a specific workspace is represented by a membership record carrying a role, and a single user can hold different roles in different workspaces simultaneously, since membership is scoped per-workspace rather than being a global property of the user account. Every workspace is required to have at least one member holding the Owner role at all times, and Aether actively refuses any action — removing a member, downgrading a role, or leaving a workspace — that would leave a workspace with zero remaining Owners. This last-owner protection exists because a workspace with no Owner would effectively become unmanageable: nobody left in that workspace would hold the permissions needed to invite a new Owner or fix the situation from the inside.

## Workspace Budgets

Every workspace is provisioned with its own monthly spending budget for language model usage, expressed in microcents, separate from every other workspace's budget and separate from the global spending cap that applies across the entire deployment. A newly created workspace receives a conservative default monthly budget automatically, without any manual provisioning step, so that a workspace can start sending chat messages immediately after creation rather than waiting on an administrator to configure spending limits first. Each workspace's budget also carries a soft-limit percentage, set well below one hundred percent by default, which exists to provide an early warning point distinct from the hard ceiling where requests actually start being rejected.

## Budget Admission Control

Before Aether allows a generation request to proceed at all, it performs a pre-request admission check using a conservative cost estimate: a local count of the prompt's tokens plus the request's maximum allowed completion tokens, priced at whichever configured model's per-thousand-token rate is currently the most expensive across the whole system. This deliberately pessimistic estimate is checked against both the requesting workspace's remaining monthly budget and the global monthly cap simultaneously, and a request is only admitted if it clears both checks independently. Using the single most expensive configured rate for this estimate, rather than the rate of whichever model the request will actually use, means admission control never needs to maintain its own per-provider, per-model pricing table separate from the one each provider adapter already reports; it only ever needs one conservative number.

## Soft Versus Hard Limits

The soft-limit percentage attached to a workspace budget does not block any requests by itself; it exists purely as a threshold for surfacing a warning before a workspace actually runs out of budget entirely. The hard ceiling is the workspace's full monthly budget figure itself, and once actual settled spend for a workspace reaches that ceiling, subsequent generation requests from that workspace are rejected by admission control until the following month's budget resets. Settled spend, which is the real, final cost of a completed generation based on the actual token counts the provider reported, is distinct from the earlier pre-request estimate used for admission: the estimate exists to decide whether to allow a request to start at all, while settlement records what a request actually cost after the fact, and Aether tracks the gap between the two as a deliberate signal for whether its estimation approach is running too conservative or too loose over time.

## Workspace Deletion and Data Export

Deleting a workspace is not an instantaneous, irreversible action taken on the spot. Requesting deletion creates a tracked deletion job and marks the workspace accordingly, after which the workspace's data is actually purged asynchronously rather than synchronously as part of the original request, mirroring the same asynchronous, job-tracked pattern document ingestion uses on the way in. A workspace can also be exported on request, producing a downloadable archive of the workspace's own data before or independent of any deletion; export requests are tracked as their own job type, separate from deletion jobs, and a completed export is made available through the same object-storage-backed, presigned-URL download mechanism documents themselves are uploaded through, rather than a separate, one-off download path built just for exports. Both deletion and export jobs are scoped strictly to the requesting workspace's own data, governed by the same row-level security and explicit workspace-identifier filtering that protects every other tenant-scoped operation, so an export request can never be used as an indirect way to read another workspace's records.

## Budget Reset Cadence

A workspace's monthly budget and the global monthly spending cap both reset on a calendar-month boundary, and settled spend tracked against either one does not carry over or accumulate across that boundary. This means a workspace that is close to exhausting its monthly budget late in a month simply regains its full budget capacity at the start of the next month, without any manual intervention or explicit reset action required from an administrator. The global cap resets on the same calendar cadence independent of any individual workspace's own budget cycle, since it exists to bound aggregate spend across every workspace in the deployment simultaneously, not to track any single workspace's usage pattern on its own.
